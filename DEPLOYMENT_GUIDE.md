# Deployment

## Local Docker deployment

Copy `.env.example` to `.env`, set a database password, and create the ingest/library directories. Preserve any existing `.env` values when updating a deployment.

Build the images, then run the password helper. It prompts without echoing the password and requires 16–512 characters. Paste the hash it prints into `PAPARR_PASSWORD_HASH` in `.env`. The password itself is not stored in configuration.

```sh
docker compose build
docker compose run --rm --no-deps paparr-api --hash-password
```

```sh
docker compose up --build -d --wait
```

Open http://localhost:5173. The UI proxies `/api` and `/health` to the backend; the API and PostgreSQL have no published ports.

The default bind address is loopback, and owner sign-in is enabled by default. For access from other machines, use an HTTPS reverse proxy, set `SECURE_COOKIES=true`, add its hostname to `ALLOWED_HOSTS`, and preserve the original Host header, including the port. The TLS proxy must overwrite `X-Forwarded-Proto` with the actual connection scheme.

Configure trust at both hops. `UI_TRUSTED_PROXY_NETWORKS` identifies the outer TLS proxy that connects to Nginx; `TRUSTED_PROXY_NETWORKS` identifies Nginx as the API's immediate proxy. Both accept semicolon-separated CIDRs. Prefer stable, specific proxy addresses such as `/32` IPv4 or `/128` IPv6 entries. A whole Docker subnet or host gateway also trusts other peers using that range or address. Keep the HTTP UI port restricted to the proxy and loopback. The UI ignores scheme headers from untrusted peers; the API independently checks its immediate peer. Unrecognized hosts and unsafe browser requests from another origin are rejected. Paparr does not terminate public TLS itself.

When upgrading an HTTPS deployment, set the new `UI_TRUSTED_PROXY_NETWORKS` explicitly. Leaving it empty causes forwarded HTTPS requests to be treated as HTTP and rejected when secure cookies are required.

`pwsh scripts/Test-TlsDeployment.ps1` exercises a local self-signed TLS proxy with disposable certificates, directories, database, and Docker network. It checks secure cookies, sign-in, CSRF, header spoofing, and session revocation. Default loopback ports are 5190 for direct HTTP and 5191 for TLS. This checks the application/proxy chain; it does not provision or validate a public certificate. `scripts/Test-ProxyTrust.ps1` separately reproduces the former header-spoof failure and tests trusted-peer and invalid-configuration cases.

The API runs as the .NET image's non-root application user. On Linux, the mounted ingest and library directories must permit that user's access (UID 1654 for the current image). Sources are retained unless `DELETE_SOURCE_AFTER_IMPORT=true`.

PostgreSQL 18 stores data under the named volume mounted at `/var/lib/postgresql`. Do not reuse an older database volume without following PostgreSQL's upgrade procedure.

## Configuration

| Variable | Purpose |
| --- | --- |
| POSTGRES_PASSWORD | Required database password |
| PAPARR_PASSWORD_HASH | Required owner password hash generated by the API helper |
| AUTHENTICATION_ENABLED | Owner sign-in, default true; disable only for a trusted local demo or test |
| SECURE_COOKIES | Require HTTPS cookies, default false for loopback HTTP; enable behind TLS |
| TRUSTED_PROXY_NETWORKS | API trust for its immediate UI/Nginx proxy; only loopback is trusted without this setting |
| UI_TRUSTED_PROXY_NETWORKS | UI trust for the immediate outer TLS proxy; empty by default, so client scheme headers are ignored |
| HOST_INGEST_PATH | Host directory to scan |
| HOST_LIBRARY_PATH | Host destination directory |
| PAPARR_PORT | UI port, default 5173 |
| BIND_ADDRESS | Host bind address, default 127.0.0.1 |
| ALLOWED_HOSTS | Semicolon-separated API hostnames, default localhost and loopback addresses |
| POSTGRES_DB | Database name, default paparr |
| DELETE_SOURCE_AFTER_IMPORT | Remove verified originals after completion, default false |
| METADATA_PROVIDERS_ENABLED | Query public metadata providers, default true |

API options also include `PollingIntervalSeconds`, `FileStableSeconds`, `MaxFileSizeMb`, `MaxAttempts`, and `LeaseMinutes`. They are validated at startup. Relative API paths resolve from the application's working directory.

## Sign-in and password changes

Paparr has one owner account. Sessions expire after eight hours and are revoked on sign-out. Generate a new hash and recreate the API container to change the password; existing sessions then lose access. There is no email reset or multi-user account management.

The `auth-data` volume stores ASP.NET Data Protection keys, and PostgreSQL stores revocable sessions. Keep both across ordinary container recreation. Restrict access to `.env`, the database, and this volume; the key files are protected by filesystem permissions, not encrypted with an external key service. Changing or losing the key volume signs users out without changing library data.

Sign-in permits five requests per minute per API process. Restarting the process resets this limit. Authentication and CSRF validation protect API mutations, including requests made outside a browser. An API client first gets `/api/auth/session`, retains the cookies, and sends its `csrfToken` as `X-CSRF-TOKEN` with sign-in. Use the replacement token returned after sign-in for subsequent mutations. Health probes remain public.

## Health and diagnosis

- `/health/live`: the API responds.
- `/health/ready`: the API can connect to PostgreSQL.
- `docker compose logs paparr-api`: import identifiers, provider failures, and publication errors.
- The review panel shows attempts, actionable failure messages, and event history.
- Worker status shows when queued imports, file maintenance, integrity scans, and discovery last made progress. `/api/diagnostics/worker` exposes the same owner-protected information.

Readiness does not certify filesystem permissions or parser health. A failed import retains its source for investigation. Repeated retries are bounded by `MaxAttempts`.

Worker diagnostics describe the API process serving the request and reset on restart. A delay indicator appears after three polling intervals without stage progress, with a minimum of 60 seconds; large files and slow storage can also trigger it. A successful stage means the worker finished that phase, even if individual imports or cleanup attempts failed. Discovery may skip inaccessible folders. Use import history and API logs to investigate; this screen does not establish global health across multiple API instances.

Optional source cleanup is tracked separately after completion. It retries up to three times, then shows a retained-source warning and a retry action. A changed source is never removed. Disabling cleanup prevents subsequent removal; it does not retroactively change already completed cleanup.

Expand **Show temporary file status** on the worker screen for publication staging counts, also available at the owner-only `/api/diagnostics/staging` endpoint. Maintenance removes only confirmed temporary files recorded in PostgreSQL, after their publication attempt stops owning the import. Current attempts remain protected even after their lease expires, until recovery changes ownership. Access failures retry with a delay; unconfirmed files are retained and logged with import and stage IDs. Settled attempts include files already absent, so the count is not a deletion total.

Files left by older versions and other untracked `.partial` files are never swept automatically. Before manually removing a retained file, stop the API, back up the database and files, and use the journal and logs to establish which attempt created it. Do not infer ownership from a filename or its age.

Library health scans compare each recorded library file with its original hash. They can resume after a restart and never repair files automatically. Verify a backup before replacing a file reported as changed or missing.

Each library row has a Download action. The server checks the file against its original hash before delivery. Changed, missing, unreadable, or unsupported files return an actionable error in the library view. Downloads do not repair files or update integrity results. Authorized API clients can use `GET /api/library/{id}/file` with HTTP byte ranges; the configured file-size limit applies.

## Calibre handoff

Choose **Export for Calibre** in a library row. The archive contains the verified original bytes as `book.epub` or `book.pdf`, approved metadata in `metadata.opf`, and instructions. Extract it into a new folder, apply the sidecar to that copy with `ebook-meta book.epub --from-opf metadata.opf` (use `book.pdf` for PDF), then add the copy through Calibre's Add books action. The command follows Calibre's [OPF import option](https://manual.calibre-ebook.com/generated/en/ebook-meta.html#cmdoption-ebook-meta-from-opf).

Applying metadata changes the exported copy. Paparr's stored file remains untouched. Missing fields in the sidecar may leave embedded metadata intact, depending on the format and Calibre's handling. Review the result in Calibre before treating it as a fully resolved edition. The server and browser buffer the archive in memory, bounded by the configured book-size limit; concurrent exports increase memory use. This is an explicit copy workflow, not synchronization or a Calibre database backup.

## Synthetic demo

With metadata providers disabled, generate fixtures in an empty ingest directory:

```powershell
pwsh scripts/New-DemoBooks.ps1 -Destination ./ingest
```

After discovery and processing, the queue contains three named books, one requiring manual metadata, and one intentionally invalid PDF. The generator refuses to overwrite existing files.

## Persistence smoke check

Run `pwsh scripts/Test-Deployment.ps1`. It creates its own Compose project and test mounts, imports a synthetic book, recreates containers, detects intentional file tampering, and restores a database dump plus a library copy into fresh locations. It also enables authentication, verifies a session through recreation, and signs out. `-Port` selects another local port. `-KeepRunning` retains an unauthenticated loopback demo after completing these checks.

The script removes only the resources it creates. Never use `down -v` on a real library deployment.

With the development Node/Playwright dependencies installed, add `-Browser` to verify the actual packaged UI: sign-in, duplicate history, manual metadata, publication, integrity scans, worker status, and sign-out on desktop/mobile layouts. Screenshots are retained under the test project's `browser` directory.

If Calibre's `ebook-meta` and `calibredb` commands are installed, add `-Calibre` to verify handoff into a new temporary Calibre library. Combining `-Browser -Calibre` also checks the archive downloaded by the browser, including manually approved edition fields. `scripts/Test-CalibreExport.ps1 -ArchivePath <export.zip>` runs the same isolated handoff check on a synthetic export; it sets a temporary Calibre configuration and removes only its own temporary library.

## Backups and restoration

For a consistent backup, stop the UI and API while keeping PostgreSQL running. Create a custom-format dump using `pg_dump --username=paparr --dbname=paparr --format=custom --file=/tmp/paparr.dump`, then copy the dump out with `docker compose cp postgres:/tmp/paparr.dump ./backup/database.dump`. Copy the library directory, ingest directory, and deployment configuration while the worker is stopped, then restart the API and UI. Keep the backup outside the live mounts.

Restore into a new empty database with `pg_restore --exit-on-error`, and copy the saved library and ingest files into separate host directories. Set `POSTGRES_DB`, `HOST_LIBRARY_PATH`, and `HOST_INGEST_PATH` to those restored locations. Keep the container paths `/library` and `/ingest`, since records store those paths. Grant the API user access, start the stack, and run an integrity scan before switching over. The deployment test exercises this procedure against synthetic data; broader PostgreSQL major-version upgrades remain unverified.

For a disaster restore, use a fresh `auth-data` volume and sign in again. Do not restore old active sessions as part of recovering library data: clear the restored `AuthSessions` table before starting the API. Session preservation is tested for ordinary container recreation; the backup test deliberately creates new sessions after restoration.
